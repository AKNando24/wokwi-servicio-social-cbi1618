# Guion 8.2 — Cliente HTTP/HTTPS: peticiones GET y POST a una API REST

**Módulo:** 8 · **Duración estimada:** ≈ 10:10 min en total (locución ≈ 5:39 min a 140 palabras/min, más demostración en pantalla)
**Archivos que se muestran:** `main.ino` (funciones `consultarClimaExterno()` y `enviarPost()`) y `libraries.txt`
**Objetivo del alumno:** entender qué es una API REST, hacer una petición GET con HTTPS y leer JSON, y enviar datos con una petición POST.

**Antes de grabar:** proyecto del Módulo 8 abierto con el monitor serie visible; prueba antes la URL de la API en el navegador para mostrar el JSON; si el video supera 10 minutos, dividir después de la escena 6.

### Escena 1 — Gancho (0:00–0:40)
**Pantalla:** el monitor serie mostrando «[GET] Temperatura exterior: 18.4 C» y la respuesta del POST.

> Tu ESP32 está en una habitación midiendo la temperatura de adentro. Pero ¿y si quisiera compararla con la de afuera? No tiene un sensor exterior, pero sí tiene Internet, y en Internet hay servicios que ofrecen esa información. En este video vas a pedirle datos del clima a un servicio en la nube y a enviar tus propias mediciones a otro. Con eso entenderás la base de casi toda la comunicación en la web.

### Escena 2 — HTTP y APIs REST (0:40–2:00)
**Pantalla:** diagrama cliente-servidor con petición y respuesta.

> HTTP es el lenguaje de la web. Un cliente, que ahora es nuestro ESP32, envía una petición a un servidor, y este devuelve una respuesta. Una API REST es un servicio web que expone sus funciones mediante direcciones y métodos HTTP, y que normalmente responde en formato JSON. Los métodos que más usaremos son dos: GET, para pedir información, y POST, para enviarla. La respuesta incluye un código de estado: doscientos significa que todo salió bien; cuatrocientos cuatro, que no se encontró lo pedido; y los de la familia de quinientos indican un error del servidor. Revisar siempre ese código es lo que separa un programa robusto de uno que se rompe a la primera falla.

### Escena 3 — La API y el JSON (2:00–3:10)
**Pantalla:** abrir la URL de Open-Meteo en el navegador y mostrar el JSON; resaltar `current` y `temperature_2m`.

> Usaremos Open-Meteo, un servicio de clima gratuito que no necesita llave de acceso. Se le pasan la latitud y la longitud en la dirección, y pide la variable temperature_2m, que es la temperatura a dos metros de altura. Así se ve la respuesta en el navegador: un JSON, es decir, texto con una estructura de llaves y valores. Dentro hay un objeto llamado current, y dentro de él, el campo temperature_2m. Nuestro objetivo es sacar ese número. Las coordenadas del código son una constante que puedes cambiar a tu ciudad.

### Escena 4 — Petición GET con HTTPS (3:10–5:00)
**Pantalla:** resaltar `WiFiClientSecure`, `setInsecure`, `HTTPClient`, `http.begin`, `http.GET` y `HTTP_CODE_OK`.

> En el código creamos un cliente seguro, porque la dirección empieza con https, y un objeto HTTPClient. Llamamos a begin con el cliente y la dirección armada con las coordenadas. Luego GET, que hace la petición y devuelve el código de estado. Si es doscientos, leemos la respuesta; si no, imprimimos el código para saber qué falló. Al final, siempre llamamos a end para liberar los recursos. Una nota de seguridad muy importante: en el curso usamos setInsecure, que acepta cualquier certificado. Es cómodo para aprender, pero en un producto real eso permitiría ataques de intermediario; ahí hay que validar el certificado del servidor con una autoridad certificadora.

### Escena 5 — Leer el JSON con ArduinoJson (5:00–6:30)
**Pantalla:** resaltar `JsonDocument`, `deserializeJson` y la expresión `doc["current"]["temperature_2m"]`.

> Para interpretar el JSON usamos la librería ArduinoJson, que declaramos en libraries punto txt. Creamos un JsonDocument, llamamos a deserializeJson con el texto de la respuesta, y revisamos si hubo error; esto es fundamental, porque la red puede devolver texto cortado o inválido. Si todo salió bien, accedemos al valor como en un diccionario: doc corchetes current corchetes temperature_2m. El operador barra vertical NaN le dice a la librería que, si el campo no existe, devuelva no es un número en lugar de cero, para no confundir una falla con una temperatura real de cero grados.

### Escena 6 — Con qué frecuencia consultar (6:30–7:20)
**Pantalla:** resaltar `PERIODO_CLIMA_MS = 60000` y el temporizador con `millis`.

> Una buena práctica con cualquier API es no abusar. El clima no cambia cada segundo, así que consultamos una vez por minuto, usando millis y no delay. Los servicios públicos suelen limitar cuántas peticiones puedes hacer; si te pasas, te bloquean. Además, cada petición HTTPS consume tiempo y energía. Pide los datos con la frecuencia que de verdad necesitas, y no más.

### Escena 7 — Petición POST (7:20–8:50)
**Pantalla:** resaltar `addHeader("Content-Type", "application/json")`, el cuerpo JSON con `snprintf` y `http.POST`.

> Ahora la dirección contraria: enviar datos. Usaremos httpbin punto org, un servicio de pruebas que devuelve en su respuesta exactamente lo que le envías. Con POST, además de la dirección, enviamos un cuerpo. Primero declaramos con un encabezado que el contenido es JSON. Armamos el texto con snprintf: temperatura, humedad y el origen del dato. Y llamamos a POST con ese texto, que devuelve el código de estado. Si es doscientos, httpbin nos regresa un JSON donde aparecen los datos que mandamos, y eso confirma que llegaron bien. En un proyecto real, este mismo patrón envía lecturas a tu propio servidor o a una plataforma en la nube.

### Escena 8 — Errores comunes (8:50–9:30)
**Pantalla:** lista de errores.

> Tres problemas típicos. Un código negativo en lugar de uno doscientos significa un error de conexión, no del servidor: revisa el Wi-Fi o la dirección. Respuestas muy largas pueden agotar la memoria si las lees completas; en un dispositivo real conviene limitar los campos que pides. Y las peticiones HTTPS tardan más que las HTTP: no las hagas dentro de partes del programa que necesiten responder en milisegundos.

### Escena 9 — Resumen y reto (9:30–10:10)
**Pantalla:** resumen y reto.

> En resumen: HTTP funciona con peticiones y respuestas; GET pide datos y POST los envía; el código de estado indica el resultado; JSON es el formato de intercambio; y ArduinoJson lo interpreta con validación de errores. Tu reto: consulta además la humedad exterior de Open-Meteo y calcula la diferencia con la lectura del DHT22. En el siguiente video vemos un protocolo hecho a medida para Internet de las Cosas: MQTT.
